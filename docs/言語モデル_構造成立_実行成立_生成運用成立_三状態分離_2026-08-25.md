# 言語モデル — 構造成立・実行成立・生成運用成立 三状態分離

状態: 作業中 / 非正本 / 再開放可

日付: 2026-08-25

---

## 0. 問題

「LLMが存在する」「LLMが実行できる」「LLMが文章を返す」を一つのPASSへ潰すと、

- checkpointだけ保存されたmodel
- runtime failure
- output surface failure
- closed API model

等の状態を正しく分けられない。

従って三状態へ分離する。

---

# 1. 構造成立

## 1.1 定義候補

> **構造成立とは、対象言語relationに対応する模型形成relationを保持するモデル同一性が、版内で確認できる状態である。**

ここでは、現在実行可能であることを必須にしない。

---

## 1.2 証拠例

- weight / config / code
- rule / table / graph
- model artifact manifest
- 言語住所規約
- source lock
- model relationの再現可能記述

### 重要

artifactがあるだけで、自動的に言語モデル構造成立とはしない。

何の対象言語relationに対応するartifactかを確認する。

---

# 2. 実行成立

## 2.1 定義候補

> **実行成立とは、現在の文脈付き内部言語状態へ模型形成relationを適用し、言語形成状態を実際に生じさせられる状態である。**

```text
文脈付き内部言語状態
→ 模型形成relation
→ 言語形成状態
```

が実行証拠として閉じる。

---

## 2.2 runtime failureとの分離

model artifactが正常でも、

- runtime dependency failure
- unsupported hardware
- missing kernel
- corrupted loading path

等で実行できないことがある。

この場合、

```text
構造成立 = 維持可能
実行成立 = 不成立 / 保留
```

と分ける。

---

# 3. 生成運用成立

## 3.1 定義候補

> **生成運用成立とは、言語形成状態を、表出作用・反復・結果接続を通じて、外部から観測可能な言語結果へ閉じられる状態である。**

```text
外部言語入力
→ 言語住所接続
→ 模型形成relation
→ 言語形成状態
→ 表出作用 / 反復
→ 外部言語結果
```

---

## 3.2 生成運用成立とモデル中核

生成運用成立には、

- tokenizer / processor
- runtime
- decoding / sampling / denoising
- output decode

等が必要になり得る。

しかし、これら全てをモデル中核componentへ昇格しない。

運用閉包の責任として記録する。

---

# 4. 三状態の組合せ

## 4.1 artifactのみ保存

```text
構造成立 = 成立
実行成立 = 未確認 / 不成立
生成運用成立 = 未確認
```

## 4.2 local model + broken tokenizer

```text
構造成立 = model relation側は成立候補
言語同一性接続 = 破損
生成運用成立 = 不成立
```

言語住所規約の破損がmodel identityまで影響するかは対象ごとに監査する。

## 4.3 closed API

```text
生成運用機能 = 観測可能
内部構造成立 = 未観測
内部実行境界 = 未観測
```

外部挙動だけから内部artifact構造を推測しない。

---

# 5. 「LLMである」の状態語

通常語の「LLMである」を一つのboolへ押し込むと情報損失が大きい。

正本では最低限、

- 言語モデル構造成立
- 言語モデル実行成立
- 生成運用成立
- 大規模資格

を別に記録する候補を置く。

外部向けに一語でLLMと呼ぶ場合でも、内部正本状態を失わない。

---

# 6. 形成過程との分離

modelが、

- trained
- authored
- compiled
- distilled
- searched

のどれで作られたかは、三成立状態とは別履歴である。

形成過程が不明でも、実行関係を観測できる場合がある。

逆に、training logがあってもruntime成立を保証しない。

---

# 7. 大規模資格との分離

構造成立した言語モデルが、

- 小規模
- 中規模
- 大規模

のどこにあるかは別資格である。

構造成立と規模判定を同じPASSへ潰さない。

---

# 8. 旧Layer-0への帰還

旧仕様では、

- model core
- execution
- output surface

が同じFunctional Coreへ混在した。

新案では、

```text
モデルrelationの存在
→ 構造成立

モデルrelationの適用
→ 実行成立

外部言語結果への閉路
→ 生成運用成立
```

と分ける。

---

# 9. 現時点の利点

- artifact保存状態をLLM喪失と誤認しない。
- runtime failureをmodel構造破綻へ誤帰属しない。
- output failureをmodel relation喪失へ誤帰属しない。
- closed APIから内部構造を逆推定しない。
- MINIDORA等の将来再監査でも、どの層が不足しているかを分別できる。

---

# 10. 次の監査

1. 構造成立にexecution evidenceをどこまで要求するか。
2. artifactだけからmodel relationを確認できない場合の状態。
3. checkpoint + config + codeを「構造成立」と呼ぶ条件。
4. closed modelのfunction-only conformanceを別状態にするか。
5. 大規模資格と三成立状態の最終状態表。
