# Layer-0 実行閉包最小契約 — 2026-08-25

## 状態

`WORKING / NOT_CANONICAL / REOPENABLE`

本書は、model artifactの最小定義と、実際にmodelを実行して結果を得るための最小契約を分離し、Execution側もcomponent列挙へ戻さず一つの遷移関係として圧縮する。

---

# 1. ArtifactとExecutionを分ける

## Artifact

```text
T = 言語対象契約
M = その有限モデル射影
C = TとMの対応適合
```

## Execution

```text
Apply(M, current_state) -> model_result
```

これを別契約とする。

---

# 2. Executionの最小形

現時点の最小候補:

> **現在状態にモデル射影を適用し、対象契約Tへ再接続可能な結果状態・関係・評価を形成する遷移。**

記号的には、説明用にだけ次を置く。

```text
S_t -- Apply(M) --> R_t
```

ここで、

- `S_t` = 現在入力・文脈・候補等を含む実行状態
- `M` = model artifact
- `R_t` = Tへ追跡可能な結果状態・関係・評価

とする。

これは物理実装形式を指定しない。

---

# 3. なぜ現在状態と結果面を別componentにしないか

旧v4では、

- context-bound state
- result formation
- result surface

を独立責任として置いた。

しかし実行契約としては、

```text
state
→ model application
→ result
```

という一つの遷移の入力面・出力面である。

物理component数へ昇格する必要はない。

外部surfaceはさらにOperational Wrapperへ分離できる。

---

# 4. 反復可能性

Generative / recurrent / iterative modelでは、結果を次の現在状態へ帰還できる。

```text
S_t
 -> R_t
 -> S_(t+1)
 -> R_(t+1)
```

方式は問わない。

- autoregressive generation
- recurrent update
- diffusion refinement
- search / graph iteration
- symbolic rewrite
- MINIDORA state transition

等を同じ上位遷移として観測できる。

反復はLanguage Model Artifact identityの必須条件ではない。

---

# 5. Generativeの定義を明確化

Generative capabilityは、実行結果`R_t`が、対象契約Tの新しい言語状態を含み、必要に応じて次状態へ再入力できる性質として置ける。

```text
Generative
=
model result が新しい linguistic state を形成可能
```

外部文字列として即時emitすることは必須でない。

---

# 6. Scoring / Representation

## Scoring LM

`R_t`が言語候補への評価・順位・適合関係でよい。

## Representation LM

`R_t`が言語単位へ対応するcontextual representationでよい。

従ってExecution contractはtext generationへ固定しない。

---

# 7. Runtimeの位置

Applyを実現するruntimeは、

- neural inference engine
- generic CPU
- Python interpreter
- rule engine
- graph executor
- database engine
- custom accelerator

等でよい。

runtimeの名称をLM identityへ含めない。

ただしruntime設定が実効relationを変える場合、

```text
M + runtime_configuration
```

を`effective model version`として別追跡することはできる。

---

# 8. state adapterの位置

外部入力をTで規定した内部stateへ接続するadapterはExecution境界に置ける。

例:

- tokenizer
- feature encoder
- HDS Compiler
- parser
- processor

ただしadapter自体が主要なlanguage modeling relationを担う場合は、単なるadapterではなくMの一部または別model artifactとして再分類する。

この判定は名称で決めない。

---

# 9. MINIDORAに対する意味

現行MINIDORAではHDS Compilerが非常に大きなsemantic transformationを担っている。

従って、

```text
Compiler = adapter
```

と先に固定してはならない。

次を監査する。

1. Compilerが外部言語→内部stateの表現変換だけを担うのか
2. Compiler自身がlanguage relation/model knowledgeを保持しているのか
3. K/C/Jが担うrelationとどこで分かれるのか
4. Compilerを外したMINIDORA model artifactにLanguage Model T/M/Cが残るのか

この結果により、Compilerのmodel identity帰属を決める。

---

# 10. 現時点の判定

- Execution minimumを`S --Apply(M)--> R`へ圧縮: **強く支持**
- state/resultを物理component数として固定: **不採用方向**
- external emissionをExecution core必須: **否定**
- iterative/recurrentをLM artifact必須: **否定**
- Generativeを結果状態の性質として定義: **支持**
- HDS Compilerを名称だけでadapter扱い: **禁止**

このExecution契約をv5最終候補へ統合する。
