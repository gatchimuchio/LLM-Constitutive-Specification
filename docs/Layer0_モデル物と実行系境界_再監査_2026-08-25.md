# Layer-0 モデル物と実行系境界 再監査 — 2026-08-25

## 状態

`WORKING / NOT_CANONICAL / REOPENABLE`

目的は、「モデル」「推論runtime」「製品system」を同一物として扱った旧Layer-0の混線を除去し、Language Modelの最小対象を定義することである。

---

# 1. 発火条件

HDS横断観測では、少なくともOpenAI系について次が明示的に分離された。

```text
model
inference
agentic harness
```

同様にMINIDORAでも、

```text
HDS-IR / 言語状態
model relationを担うP/K/言語基底等
Layer0/K/J等の実行作用
CLI/API/表面化
```

は同一物ではない。

従ってLayer-0は「モデル物」と「モデルを動かしたsystem」を区別する。

---

# 2. 三対象を分ける

## 2.1 言語モデル物

版として同定可能で、複数の言語状態へ再利用される**言語状態間の関係仕様**。

実体は問わない。

- weights
- rules
- conditional table
- graph
- compiled program
- hybrid relation set

等を許容する。

言語モデル物は、それ自体が現在入力を保持している必要はない。

## 2.2 言語モデル実行系

現在の言語状態へ言語モデル物を適用し、結果状態・関係・評価を形成する実行系。

```text
Run(Model, LinguisticState) -> LinguisticResultState
```

ここに、

- forward executor
- recurrent engine
- rule interpreter
- graph executor
- generic CPU/Python runtime
- inference kernels

等が入り得る。

## 2.3 展開system

モデル実行系へ、

- API
- tokenizer/processor service
- scheduler
- cache manager
- speculative serving
- tools
- RAG
- persistent memory
- safety classifier
- fallback
- agent loop

等を接続した展開物。

これをmodel-only claimへ逆帰属しない。

---

# 3. 新Layer-0の対象候補

「LLMとは何か」を最小定義する場合、最上位対象はまず**言語モデル物**である。

その最小契約候補は二つ。

## M1. 言語状態域契約

モデルの入力側・結果側が、言語の単位・関係・順序・構造・意味・候補・評価へ追跡可能に接続されること。

表面text/tokenである必要はない。

## M2. 再利用可能なモデル関係

同一versionとして追跡可能な関係仕様が、複数の言語状態に対して適用可能であり、言語状態または言語候補間の関係・評価を規定すること。

ここでいう「関係仕様」はlearned parameterへ限定しない。

---

# 4. 実行可能性は別契約

モデル物だけでは観測可能な挙動は発生しない。

従ってOperational Conformanceでは追加で、

## X1. 現在言語状態

実行時の入力・文脈・候補等。

## X2. 適用作用

モデル関係を現在状態へ適用するexecutor。

## X3. 結果状態接続

実行結果を言語状態・関係・評価として追跡可能にすること。

を確認する。

ただしX1-X3を**モデル物の構成要素数**として数えない。

---

# 5. 重要な帰結

## 5.1 isolated weightsはモデルであり得る

重みobject単体にCLIやdecoderがなくても、言語状態域契約とmodel relationを保持するならmodel artifactとして同定できる。

「外部出力できないからLLMではない」という旧system-oriented定義は採用しない。

## 5.2 runtime差で挙動が変わる

同じmodel artifactでも、

- quantization
- sampling/argmax
- cache
- speculative execution
- routing
- processor

等で可観測挙動が変わる。

その差をmodel artifactへ無条件に逆帰属しない。

ただしruntime設定が実効関係を変更する場合、`effective model version`として別同一性を付すことはできる。

## 5.3 model identityは不変性ではなく追跡可能性

online update、adapter、LoRA、runtime patch等でmodel relationが変化し得る。

従って「永久固定」を要求せず、

```text
model_id
version
relation_contract
source/provenance
```

で変化を追跡する。

# 6. 反例への適用

## sentiment classifier

言語encoder artifactがM1/M2を満たす場合、encoderはLM candidateになり得る。

classifier headは固定task labelへ写す別application relationである。

system全体をそのままLLMとしない。

## calculator

parse後の主要model relationが算術状態上の演算なら、M1の言語結果域閉包を失う。

自然言語I/Oはwrapperである。

## parser / grammar

言語状態から言語構造を形成し、同じgrammar relationを複数状態へ再利用する場合、LM artifact候補になり得る。

Largeかどうかは別profile。

## exact retrieval

query->stored response の対応表も形式上はrelation artifactであるため、M1/M2だけでは排除できない。

ここをCoreへ禁止規則として押し込むと、n-gram tableやcompiled modelとの境界が恣意的になる。

従ってexact retrievalの縮退は、

- 組合せ開放性
- 関係形成性
- 結果域開放性
- instance memorization dependence

等のprofile/negative controlで扱う方向がより整合的である。

---

# 7. R1/R2/R3再判定

前段の三論理役割:

```text
R1 言語状態域
R2 モデル関係
R3 実行作用
```

を次へ改訂する。

```text
Model Artifact Layer
  M1 言語状態域契約
  M2 再利用可能なモデル関係

Execution Layer
  X1 現在言語状態
  X2 適用作用
  X3 結果状態接続
```

R3は重要だが、Model Artifactの第3不可約部品ではない。

---

# 8. Layer-0候補の意味

新Layer-0は一枚のcomponent listではなく、最低でも次の二面を持つべきである。

```text
Layer-0M = Language Model Artifact Minimum
Layer-0X = Language Model Execution Minimum
```

その上に、

```text
Layer-L = Large / Language-domain Profile
Layer-C = Capability Profile
Layer-T = Compute Topology
Layer-F = Formation
Layer-O = Operational Wrapper
Layer-A = Application/Agent
```

を置く。

---

# 9. 現時点の判定

- model / inference / harness分離: **確定的に必要**
- R3実行作用をmodel artifactの必須componentとして数える: **否定方向**
- model artifact最小候補=M1+M2: **強く支持、未確定**
- execution conformanceを別Layer-0Xへ分離: **強く支持**
- exact retrievalをCoreの名称禁止で排除: **不適切**
- exact retrieval縮退をprofile/negative controlへ送る: **より整合的**

次はM1/M2を一つの「言語モデル関係」へ統合できるか、またLarge profileがexact retrieval / narrow parser / unigram / classifierをどの程度自然に分離するかを監査する。
