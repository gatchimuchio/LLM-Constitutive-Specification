## 2. 「言語接続状態域」と「文脈有効関係」は統合可能

文脈は、独立した物体ではなく状態間の関係・順序・条件・履歴である。

したがって、内部状態が、

- 言語単位
- 言語差異
- 状態間関係
- 順序
- 条件
- 履歴

を現在処理へ有効な形で保持できるなら、

```text
言語接続状態域
+
文脈有効関係
```

は、

```text
言語文脈状態
```

へ情報損失なく統合できる。

ここで「状態」はpersistent memoryだけを意味しない。

- token sequenceを毎回再計算する
- KV cacheを持つ
- recurrent stateを持つ
- graphを持つ
- HDS座標・関係を持つ

のどれでもよい。

必要なのは、**現在結果を変え得る言語・文脈差を内部で区別できること**である。

---

## 3. 「言語結果形成」はモデル作用へ統合可能

モデル作用を、

> 現在の言語文脈状態を入力として、新しい言語接続状態・関係・評価を形成する再利用可能な作用

と定義すれば、結果形成は作用の出力側である。

従って、結果形成を独立責任にすると、関数の出力を関数本体と別の不可約責任として二重計上する可能性がある。

外部文字列化・API・score surface等はOperational Wrapperへ置く。

---

## 4. 2責任候補

### A. 言語文脈状態

> 言語に接続された単位・差異・関係・順序・条件・履歴を、現在処理の結果へ作用可能な内部状態として区別できること。

要点:

- language tokenそのものを必須としない。
- HDS座標、semantic relation、graph node、embedding等を許容する。
- contextを別componentとして要求しない。
- 状態は入力ごと・時点ごとに変化し得る。

### B. モデル作用

> 版として同定可能で再利用可能な作用が、現在の言語文脈状態へ適用され、参照・評価・関係形成・変換・合成・更新のいずれかを通じて、新しい言語接続状態・関係・評価を形成できること。

要点:

- neural weightを必須としない。
- authored rule / compiled operator / graph operation / retrieval + composition等を排除しない。
- 作用は一入力専用の固定応答ではなく、複数の言語文脈状態へ再利用可能である。
- 出力表面は作用の結果を観測するwrapperであり、model core内部責任ではない。

---

## 5. なぜAとBは統合しないか

AとBには時間的・役割的な非対称性がある。

### A: 可変状態

- promptごとに変わる
- contextごとに変わる
- turnごとに変わる
- diffusion stepごとに変わる
- recurrent stepごとに変わる

### B: モデル同一性を保持する作用

- 同一model version内で複数状態へ再利用される
- 状態が変わっても作用規則のidentityは維持される
- weight / rule / compiled mapping / graph operator等として実装され得る

従って、

```text
可変な状態
≠
状態へ再利用される作用
```

であり、この二つは現時点で統合できない。

## 7. 除去監査

### Aを除去

Bの作用規則だけが残る。

しかし、現在どの言語差異・関係・文脈へ作用すべきかを表現する対象状態がない。

結果:

- 固定挙動
- 無対象関数
- 非言語的定数生成

へ縮退する。

`A = 必要候補`

### Bを除去

Aの言語文脈状態だけが残る。

しかし状態へ作用して次状態・評価・関係を形成するmodel identityがない。

結果:

- 保存
- 表示
- opaque memory
- passive representation

へ縮退する。

`B = 必要候補`

## 8. 境界反例

### unigram

文脈関係を保持しないため、Aの「現在結果へ作用可能な文脈差」が弱い／欠ける。

歴史的Language Modelとしては成立しても、今回のcontextual LM core候補からは外れる可能性がある。

この点は「LM一般」と「現代LLM機能核」の境界としてOPEN。

### n-gram

有限でも文脈状態と条件付きmodel作用を持つためA/Bを満たす。

Large側で規模・適用域を評価する。

### exact retrieval

query stateとlookup mappingを持つため形式上A/Bへ近い。

従って、A/Bだけではexact retrievalを排除できない。

これはA/Bの欠陥とは限らない。`model`と`retriever`を構造的に区別するために「未列挙組合せへの作用再利用」等をBへ含めるか、Large/Generality profileへ送るかを次に監査する。

### calculator

A/Bを部分的に満たし得る。

しかし言語状態域・結果域・領域横断性が極端に狭い。Large profileで縮退する。
