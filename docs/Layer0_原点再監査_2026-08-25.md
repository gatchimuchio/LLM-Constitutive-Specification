## 状態

- 状態: `WORKING / NOT_CANONICAL`
- 規定言語: 日本語
- 目的: 既存Layer-0を前提にせず、「LLMとは何か」を機能・境界・状態・作用・結果から再観測し、最小構成候補を再抽出する。
- 現行v4正本は変更しない。本書の再監査が閉じるまで比較対象・履歴として保持する。

## 1. 再開放の発火条件

MINIDORAのHDS-IR経路をGPQA等へ適用する過程で、完全HDS-IRへ意味情報を追加しても計算性能が単調に改善せず、現行Kが実際に読む情報が限定されていることが確認された。

現行MINIDORAの候補比較では主として次が使われる。

- 語集合
- 関係種別
- 座標種別
- 始点→関係→終点の有向辺

直接関係検証ではさらに、

- 関係
- 始点
- 終点

へ縮退する。

このため、次の疑いが発生した。

1. HDS Compilerが「完全意味Projection」と「計算核向けlowering」を分離できていない。
2. MINIDORAが参照するLayer-0責任契約と、実際の計算核が要求する入力契約の粒度が一致していない。
3. Layer-0自体が、LLMの適合監査責任と計算機としての最小構造を混同している可能性がある。

この疑いを先に確定せず、Compiler・MINIDORA・Layer-0を順次修正することを禁止する。

## 3. 横断再観測で確認できたこと

### 3.1 既存の粗い実装分類はLayer-0にならない

Dense / MoE、Attention / recurrent、local / global等は実装差であり、LLMの成立条件そのものではない。

横断HDSでは少なくとも次の情報流が独立して観測されている。

- 系列方向の情報流
- 深さ方向の情報流
- 幅方向の情報流
- 未来方向・予測補助
- 入力表象・モダリティ前段
- 形成過程
- 展開後制御

したがって、特定機構名をLayer-0へ昇格しない。

### 3.2 「選択・圧縮・疎化」は普遍必須ではない

DeepSeek V4、Qwen3.6、K3では、圧縮、top-k、recurrent更新、MoE routing等が強く観測される。

一方、Llama 3やK2-V2はDense / global GQAで成立する。

したがって、

- 選択
- 圧縮
- top-k
- sparse routing
- delta-only更新

をLLM成立の普遍必須条件へ直接昇格しない。

これらは主として効率・能力・情報輸送方式の候補であり、Layer-0機能核とは分離して保持する。

### 3.3 それでも一段下には共通作用が残る

異なる実装を横断して残る候補は次である。

1. 言語に接続された内部状態を持つ。
2. 現在の処理が文脈状態の差に依存する。
3. 固定されたモデル作用により、状態同士の参照・関係形成・変換・統合・更新のいずれかを行う。
4. その結果から、言語へ接続可能な結果状態を形成する。

現時点では、これが実装方式を横へ引いたときに最も小さく残る作用候補である。

### 3.4 モデル本体と周辺実行系を分ける必要がある

既存HDS横断観測では、少なくとも次を同一物へ潰せない。

- model core
- inference runtime
- agentic harness
- safety classifier / fallback / router
- product tool integration

同一underlying modelでも展開後制御により可観測挙動が変わる例がある。

従って、LLMの定義へagent harness、tool use、safety routing、product UI等を混入しない。

### 3.5 形成方法と実行機能を分ける

次はモデルの作られ方であり、実行時Layer-0の必須作用とは限らない。

- pretraining
- posttraining
- SFT
- preference optimization
- RL
- authored rules
- compilation
- search / induction

「学習済みであること」をLLM成立条件へ先置きしない。

## 4. 旧Layer-0に対する再判定

### v3以前

旧6要素系は、現代LLMの通常語義を先に固定し、`learned parameterized transform`、`sequence-modeling objective`、`decoding/emission interface`等を定義へ含めていた。

今回の原点再監査では、この方法を採用しない。

理由:

- constructionとruntimeを混同する。
- model coreとoperational wrapperを混同する。
- 非ニューラル／compiled／authored候補を定義だけで排除する。
- 「既存LLMがそう作られている」ことと「LLMであるために不可欠」を混同し得る。

### v4

v4は上記問題を既にかなり再開放している。

- 5責任を暫定語彙とする。
- exact minimumをOPENとする。
- construction / provenanceをFunctional Coreから分離する。
- Operational Wrapperを分離する。
- neural / symbolic / graph / retrieval + composition等を名称だけで排除しない。

したがって、v4を全面否定しない。

ただしv4の5責任は、候補システムを監査する**適合責任語彙**としては有効でも、計算機が何を入力し何を状態として保持し何を作用させるかを規定する**計算契約**としては粗い。

今回の主要な誤り候補は、v4を計算アーキテクチャ／Compute ABIの代わりとして下流へ使用したことである。

## 5. 日本語による原点定義候補

以下は再監査中の候補であり、正本ではない。

### 5.1 「モデル」

モデルとは、版として同定可能な作用規則を保持し、同じ種類の状態へ再利用可能な変換・関係形成・遷移を与えるものとする。

作用規則の形成方法は問わない。

- 学習
- 人手記述
- compilation
- induction
- search
- hybrid

を同じruntime定義へ混入しない。

### 5.2 「言語モデル核」暫定定義

> 言語モデル核とは、言語に接続された状態を扱い、現在の文脈状態に応じてモデル作用を適用し、状態を関係付け・変換・更新し、その結果から言語へ接続可能な結果状態を形成する計算核である。

この定義は確率、ニューラルネットワーク、Transformer、Attention、MoE、学習済みparameter、next-token方式を前提としない。

### 5.3 暫定4責任

#### A. 言語状態接続

外部の言語差異を内部で参照可能な状態へ接続できること。

実装例:

- token / token ID
- embedding
- 記号表
- HDS座標
- graph node
- parser state

特定方式を必須としない。

#### B. 文脈有効状態

現在の処理に関係する既出状態・系列・条件の差が、後続結果へ作用できること。

物理的なpersistent memoryを必須としない。現在入力全体を再計算する方式でも、文脈差が内部状態として有効なら候補となる。

#### C. 文脈依存モデル作用

版として同定可能なモデル作用が、現在状態へ参照・関係形成・変換・合成・統合・更新のいずれかを与え、固定反射や単純な全体一致検索だけではない次状態を形成できること。

系列・深さ・幅の情報流はこの責任の実装座標として別々に監査する。

#### D. 言語結果形成

モデル作用後の状態から、言語単位・言語構造・言語候補・言語に対応するscore等へ接続可能な結果状態を形成できること。

外部APIや文字列表示そのものは必須としない。結果表面はoperational wrapperとして分離する。

## 6. 「大規模」の扱い

`Large`をLayer-0の独立作用として扱わない。

大規模性は、少なくとも次のような**規模・汎用性プロファイル**としてFunctional Coreの外側で評価する候補とする。

- 言語状態域の広さ
- 未知組合せへの適用範囲
- 文脈容量
- 関係・変換の再利用範囲
- 結果形成域の広さ
- 特定タスク専用コードなしで扱える領域幅

固定parameter数を定義へ直結させない。

ただし、どの閾値から「大規模」と呼ぶかは現時点ではOPENとする。

## 8. 反例監査候補

新4責任は次で崩す。

1. 固定応答器
2. 完全一致retrievalのみの系
3. 文脈を無視するunigram型
4. 言語入力を受けるだけのencoder / embedding系
5. 固定ラベル分類器
6. 狭い自然言語calculator / parser
7. autoregressive LM
8. masked LM
9. diffusion LM
10. recurrent LM
11. Dense Transformer
12. MoE Transformer
13. MINIDORA
14. modelなしagent harness
15. model core単体とdeployed serviceの境界差

狭いcalculator等が4責任を満たす場合、4責任は「言語計算核」の条件にはなっても「大規模言語モデル」の十分条件ではない。その差は大規模性／汎用性プロファイルで閉じる必要がある。

## 9. 現時点の判定

### 誤り仮説

`SUPPORTED / NOT YET CLOSED`

- HDS Compiler: 完全意味ProjectionとCompute loweringの分離不足が強く支持される。
- MINIDORA: 全体として状態・差分を持つため「状態がない」は誤り。ただしK実計算契約と上位HDS-IRの粒度不一致がある。
- Layer-0: v4適合責任語彙そのものは有効性を保持するが、LLM最小計算構成／Compute ABIとして使うには不足する。

### 現時点で否定したもの

- 「選択がLLM普遍必須」
- 「圧縮がLLM普遍必須」
- 「delta更新がLLM普遍必須」
- 「学習済みparameterがLLM普遍必須」
- 「Result Surface/APIがmodel coreの必須内部機構」

### 現時点で残る最小候補

```text
言語状態接続
＋
文脈有効状態
＋
文脈依存モデル作用
＋
言語結果形成
```

これはまだ最終最小性を主張しない。
